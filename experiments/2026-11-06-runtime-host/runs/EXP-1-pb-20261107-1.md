## How each fault was reached

- **The suite's named crash points** (`stop-after-received`, `stop-after-computed`, `stop-after-durable`): through
  `testing::FaultSeam`, in-process. The store stops its submit after the point; the harness's kill drops the host,
  closing its log and releasing its lock, and keeps its directory. Nothing is buffered in user space, so this
  leaves the log as a killed process would.
- **The suite's kills between submits** (`acknowledged-records-survive-a-kill`, `halt-survives-a-kill`,
  `released-records-survive-a-kill`, `repeat-after-a-kill`, `stop-during-import-is-refused-at-open`): the same
  kill, through `testing::Harness`.
- **The swap cells**: in three directions, each its own report below: `pb` to the reference host, `pb` to `pb`, and
  the reference host to `pb`, so the store is scored both as the host exported from and as the one imported into.
- **A real process kill**, beyond the suite: the test re-runs its own binary as a writer process on a store
  directory and kills it with SIGKILL (`Child::kill`), twelve times on the same store, each after a set number of
  new acknowledgements and a set delay, to vary where in a submit each kill lands. In this run the test printed
  `real-kill: 12 kills, 122 records acknowledged, 11 kills landed after the write of the record in flight and before
  its acknowledgement`. The twelfth did not land in that window (it is not known where it landed). Where between the write and the acknowledgement each
  landed was not measured. On a local file system a SIGKILL doesn't tear one write, which is why the torn-write
  test cuts the log by hand. After each kill the store is reopened in the test's own process and checked.
- **A torn write**, beyond the suite: the log's last frame cut 1, 4, 8 and 9 bytes in, half way and one byte short
  of whole, and given a flipped byte, each on its own copy of the store (7 tails, by the test's list).
- **Damage past one append**, beyond the suite: the last three frames zero-filled, a byte flipped in each of the
  last three, the last frame alone zero-filled (its length unreadable), and bytes past the length the last header
  declares, each on its own copy.
- **A failed write, a failed sync and a failed undo**, beyond the suite: unit tests inside the module, through a
  seam compiled only under `cfg(test)`, and one with no seam that swaps the host's log handle for a read-only one.
- **Damage inside an import**, and **the start of an import**, beyond the suite: by the integration tests in the
  table below.
- **Not reached**: a power loss before a sync. A process kill keeps the operating system's page cache, so no test
  here can show it. Durability across a power loss rests on the store's sync calls, which its module documentation
  states (on macOS `fcntl(F_FULLFSYNC)`, on Linux `fdatasync`), and is read, not run.
- **Not reached**: a crash between a failed sync and the cut that undoes it, and a marker that can't be written
  after an undo that failed. The module documentation states both windows.
- **Not run**: a journal past 1,024 entries or 64 MiB, the store's size caps, and throughput and latency (which no
  target claims before `M4`, `PLAN.md` §6.2, risk 9); `EXP-1-pb-20261107-2` measures them.

## A gap for `EXP-1` to score

Every append is one frame, synced before the next, so only the last frame can be torn, and recovery never cuts more
than that one frame; anything larger with no whole frame in it is refused, not cut. Two cases remain, both about
that last frame:

- **Damage confined to the last frame, its length intact,** can't be told apart from a torn write, so the store cuts
  it as one, as `a_log_torn_mid_record_reopens_at_its_last_whole_record` shows with a flipped byte. If that last
  entry was acknowledged and the media damaged it afterwards, it is lost without a refusal: at most one acknowledged
  entry. The frame's CRC-32 detects the damage but not why: a torn write and later damage both fail it the same way.
- **A torn last frame whose length is unreadable,** such as a zero-filled block a file system may leave after a
  power loss, is refused rather than cut, because it can't be told apart from several zeroed frames. Nothing is
  lost, but the store needs an operator before it opens.

The module's documentation said "only a checksum or a copy kept apart from the log could tell the two apart" while
its frames carry a checksum. At this run's commit the sentence was still there; the checksum catches the damage but not
its cause, and a later commit (`a916087`) rewrote the sentence to say so. No code changed.
