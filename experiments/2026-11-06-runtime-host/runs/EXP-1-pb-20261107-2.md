## How each fault was reached

No fault is injected. `G-01` kills the host (the harness's in-process kill: drop the host, keep the directory) and
reopens the store from its log alone, to read the journal back from disk.

## `G-01`: a journal past 1,024 entries and 64 MiB

`g01_a_journal_past_1024_entries_and_64_mib_replays_whole`. One order: its route chosen, then 1,200 settled-segment
inputs of about 80 KB each under distinct record ids, every one submitted and synced. The criterion is the one VOS
was scored on: run `H-17`'s replay on a journal past the report's compaction defaults of 1,024 entries and 64 MiB.
`H-17`'s own check is a suite cell and was not re-run on this journal; the test makes its check by hand, folding
`open` and `transition` of the probe over the journal's inputs in sequence order, through the state machine alone,
and comparing each result with the recorded state, before the kill and after the reopen. It also checks the journal
read back after the reopen is equal to the one before.

```text
G-01: one order, 1201 journal entries, 97612570 bytes of journal JSON (93 MiB), log file 97653529 bytes; replay through the state machine alone matched every recorded state, 1201 entries before the kill and 1201 after the reopen; written in 7.6s, reopened in 339.6ms
```

Result: pass. The log is never compacted: 1,201 entries and 93 MiB of journal JSON were all there after the reopen,
each recorded state reached by the fold. The reopen reads the whole log and took 0.3 s.

## `G-32`: the store's caps

`g32_the_frame_cap_and_the_largest_record_it_accepts`. The store has one size cap: a frame's payload, one log entry
(a record or a refusal in its envelope), is at most `MAX_PAYLOAD`, 64 MiB (67,108,864 bytes), behind an 8-byte header.
It has no cap on a key, a value or a request, no cap on the writes of a step, and none on the number of entries of
a journal. The test measures the frame at two sizes to get its fixed part and slope, predicts the largest that
fits, and checks the edge: that is accepted, one more byte (or part) is refused. It also records whether the host
goes on afterwards.

```text
G-32 evidence: frame cap 67108864 bytes (64 MiB) of payload, behind an 8-byte header (4-byte length, 4-byte CRC-32); a settled input's frame payload is 1362 bytes plus 1 per byte of evidence id; the longest accepted has evidence of 67107502 bytes: payload 67108864 bytes, input JSON 67107776, state JSON 1008; one byte more is refused with Unavailable { reason: "an entry is larger than a frame holds" }; the host goes on after the accepted record: true, after the refused one: true
G-32 parts: a route chosen's frame payload is 633 bytes plus 1422 per part of three segments; the most parts accepted is 47192: payload 67107657 bytes, input JSON 28834570, state JSON 38272882; one part more is refused with Unavailable { reason: "an entry is larger than a frame holds" }; the host goes on after the accepted record: true, after the refused one: true
```

Result: pass. The largest input accepted is 67,107,776 bytes of JSON (the evidence id grows only the input); with
the route's parts, which grow the input and the state together, the largest record has an input of 28,834,570 bytes
and a state of 38,272,882 bytes (47,192 parts of three segments). Over the cap, the submit is refused with
`Unavailable` before anything is written, and the host goes on: a later small input is recorded. The measure does
not cover the contract's own largest fixture, nor a refusal's frame, which wraps an input the same way and so has the
same cap.

## `G-42`: sequential synced throughput

`g42_sequential_synced_submits_per_second`. Method: one host on one fresh store, one thread; the probe scenario's
orders (`ord-0` to `ord-399`, seven inputs each: 2,800 submits); each submit is a new record id, is written with one
`write_all` and synced (`sync_data`, which on macOS is `fcntl(F_FULLFSYNC)`) before it returns; the time of each
submit is taken with `Instant`, and the round's total from the first submit to the last. Three rounds per
invocation, each on a fresh store. Release build. One host and one disk: not a measurement beyond them, so what
`G-42` asks for beyond one host sharing one disk is not measured.

The invocation whose numbers the cell quotes (the second, run with the final test code):

```text
G-42 round 1: 2800 sequential synced submits in 13.67s = 205 submits/s; per submit p50 4.89ms, p99 7.35ms, max 26.45ms; log 3957065 bytes
G-42 round 2: 2800 sequential synced submits in 13.86s = 202 submits/s; per submit p50 4.87ms, p99 8.04ms, max 44.07ms; log 3957065 bytes
G-42 round 3: 2800 sequential synced submits in 13.42s = 209 submits/s; per submit p50 4.81ms, p99 7.42ms, max 25.82ms; log 3957065 bytes
```

The first invocation, of the same measurement:

```text
G-42 round 1: 2800 sequential synced submits in 14.15s = 198 submits/s; per submit p50 4.76ms, p99 9.32ms, max 95.32ms; log 3957065 bytes
G-42 round 2: 2800 sequential synced submits in 14.08s = 199 submits/s; per submit p50 4.74ms, p99 11.90ms, max 154.70ms; log 3957065 bytes
G-42 round 3: 2800 sequential synced submits in 15.54s = 180 submits/s; per submit p50 5.17ms, p99 10.71ms, max 26.69ms; log 3957065 bytes
```

Result: `fail` for `G-42`, which asks for throughput and p99 latency measured beyond one host sharing one disk, and
this run measured on one host and one disk; VOS is scored `fail` on the same thing. The measurement itself stays:

- The final invocation, run with the committed test code: 202 to 209 submits per second, a median of 4.8 to 4.9 ms
  and a p99 of 7.35 to 8.04 ms per submit; the slowest single submit 44.07 ms. This is what the sheet's cell quotes.
- The first invocation (180 to 199 submits per second, p99 9.32 to 11.90 ms, slowest 154.70 ms) ran before the
  `G-32` test of the same file was rewritten; the `G-42` test was the same. Nothing in the code explains the slower
  rounds, and this run did not find the cause (a drive's flush time varies). It is listed above for completeness and
  is not quoted by the sheet.

Each submit syncs once, and the median submit is about 5 ms; this run did not separate the sync's share of it from
the rest.
