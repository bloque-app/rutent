## How each fault was reached

- **The suite's named crash points** (`stop-after-received`, `stop-after-computed`, `stop-after-durable`): through
  `testing::FaultSeam`, in-process. The store stops its submit after the point; the harness's kill drops the host,
  closing its log and releasing its lock, and keeps its directory. Nothing is buffered in user space, so this
  leaves the log as a killed process would.
- **The suite's kills between submits**: the same kill, through `testing::Harness`.
- **The swap cells**: in three directions, each its own report below: `pb` to the reference host, `pb` to `pb`,
  and the reference host to `pb`, so the store is scored both as the host exported from and as the one imported
  into.
- **A real process kill**, beyond the suite: the test re-runs its own binary as a writer process on a store
  directory and kills it with SIGKILL (`Child::kill`), twelve times on the same store, each after a set number of
  new acknowledgements and a set delay, from 0 to 9 ms, to vary where in a submit each kill lands. In this run 11
  of the 12 landed after the in-flight frame's `write` and before its acknowledgement, and the one with no delay
  landed before the write; where between the write and the acknowledgement each landed was not measured. None landed inside a `write`: on a local file system a
  SIGKILL doesn't tear one write, which is why the torn-write test below cuts the log by hand. After each kill the
  store is reopened in the test's own process and checked.
- **A torn write**, beyond the suite: the log's last frame is cut 1, 4, 8 and 9 bytes in, half way and one byte
  short of whole, and given a flipped byte, each on its own copy of the store.
- **Damage past one append**, beyond the suite: the last three frames zero-filled, a byte flipped in each of the
  last three, the last frame alone zero-filled (its length unreadable), and bytes past the length the last header
  declares, each on its own copy.
- **A failed write, a failed sync and a failed undo**, beyond the suite: unit tests inside the module, through a
  seam compiled only under `cfg(test)` (`Inject`): a write that stops half way and fails; a whole write whose sync
  fails; and a sync that fails followed by an undo that fails. A fourth test uses no seam: it swaps the host's log
  handle for one opened read-only, so the write and the undo both fail for real.
- **Damage inside an import**: a byte flipped among the imported records of an import that finished and was then
  used, and among the records of an import stopped part-way.
- **The start of an import**, beyond the suite: the harness's seam stops an import right after its first frame is
  synced, before any of the stream, and after the stream's header; and that first frame is torn three ways.
- **Not reached**: a crash after a failed sync and before the undo cuts the frame. If the frame then reads back
  whole, it is taken as a record present and unacknowledged; if damaged or zeroed, it is refused as damage. The
  module documentation states the window.
- **Not reached**: a marker that can't be written after an undo that failed. The host then stays stopped, but
  nothing on disk refuses the next open; the module documentation states it as the one case not covered.
- **Not reached**: whether syncing the directory on every open makes the log's name durable across a power loss;
  like the next item, it rests on the code.
- **Not reached**: a power loss before a sync. A process kill keeps the operating system's page cache, so no test
  here can show it; it rests on the store's sync calls, which the store's module documentation states (on macOS,
  `fcntl(F_FULLFSYNC)`; on Linux, `fdatasync`), for `EXP-1` to score by reading the code.

## A gap for `EXP-1` to score

Every append is one frame, synced before the next, so only the last frame can be torn, and recovery never cuts
more than that one frame: anything larger with no whole frame in it is refused, not cut
(`damage_to_more_than_the_last_append_refuses_the_store_and_cuts_nothing`). Two cases remain, both about that last
frame:

- **Damage confined to the last frame, its length intact,** can't be told apart from a torn write, so the store
  cuts it as one, as `a_log_torn_mid_record_reopens_at_its_last_whole_record` shows with a flipped byte. If that
  last entry was acknowledged and the media damaged it afterwards, it is lost without a refusal: at most one
  acknowledged entry.
- **A torn last frame whose length is unreadable,** such as a zero-filled block a file system may leave after a
  power loss, is refused rather than cut, because it can't be told apart from several zeroed frames. Nothing is
  lost, but the store needs an operator before it opens.

Only a checksum or a copy kept apart from the log could tell either apart. This is recorded as a gap for `EXP-1`
to score against every candidate, not a defect fixed here.
