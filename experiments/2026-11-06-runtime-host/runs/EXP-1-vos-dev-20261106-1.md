## How each fault was reached

The host is the adapter in this process plus one `vos node run` process on the store's data directory. A store is
that directory; a kill is a `SIGKILL` of the node, and a reopen starts it again on the same directory.

| Fault | How |
|---|---|
| Kill and reopen | `SIGKILL` of the node between submits, then `vos node run` on the same data directory |
| Stop after received | Through `FaultSeam`: the adapter holds the input, nothing is computed or sent, and the node is killed |
| Stop after computed | Through `FaultSeam`: the adapter computed the transition; VOS's fault file was set to `hold_commits` and the node confirmed it (`generation`); the append was sent; the node was killed 1 s later. Held, VOS could not have made it durable. That VOS had received the append by then is inferred, not observed: the `control-no-hold` pass sends the same append without the hold, and the record is then present after the reopen, so the append reached VOS within the 1 s, and the hold, not the timing, kept it out |
| Stop after durable | Through `FaultSeam`: VOS answered the append as run, so it had committed it; the node was killed before the adapter returned |
| Stop during an import | A kill between two entries' calls, after 1, half and all but the end entry |
| Swap mid-order | Halt, export, import into the other implementation on a fresh store, resume: VOS to the reference host (`vos-to-ref`, `compacted`) and the reference host to VOS (`ref-to-vos`), so VOS was scored as exporter and as importer |
| Log compaction | VOS's fault file's start-time setting `compact 16 4`: the agent's Raft log compacts every 16 entries to a tail of 4 (`compacted`, `compaction`). It stands in for VOS's defaults, 1,024 entries or 64 MiB to a tail of 256 (`node/host/src/node/config.rs:211-217`), which these passes' few hundred records would not reach |
| Session expiry | VOS's `clock` fault moves the node's clock ahead: 61 min, past the hour after which a session expires (`agent/wire/src/defaults.rs:6`), then 75 min, past the five-minute bucket in which it is collected (`:13`) (`session-expiry`) |

**A refused import** (`H-15`) leaves the new store marked as importing, so `open` refuses it; the import is redone on
a fresh store. The reference host does the same (`components/stm/src/reference_host.rs`, `import_onto`), and the
contract asks nothing of a store an import refused.

**Where the state machine runs.** In the adapter, not in VOS. rutent's state-machine contract needs `std` and
`serde`, and a VOS guest is `no_std` on RV64EM with no atomics (`pvm/guest/README.md:3-6`), so a guest can't run
it without a port. The adapter reads the order's latest state from VOS, computes the transition, and sends the
record. Every rule that needs state is the journal actor's, checked in one handler step that VOS commits whole
(`docs/design/core-model.md:505-510`): halted, the record id against byte-equal canonical JSON, the order's next
sequence number as a compare-and-set, and an open import. The adapter holds nothing authoritative, so a kill
drops nothing the contract needs.

**Power loss and torn writes**, which the suite can't produce (`conformance/README.md`, Not covered), by reading
VOS's code:

- A single-node commit needs the leader's own durable append. A member's score is `durable_index` for the leader
  itself (`support/vos-raft/src/core/replication.rs:512-520`), and the commit index moves only to the majority
  floor of those scores (`:528-534`).
- Log appends, truncations, terms and votes are synced before their commit is answered. Applies and compactions
  are not, and a restart replays the log over them (`node/host/src/storage/mod.rs:1-16`, `:143-163`).
- The writer stages a group of commits in one fjall batch and commits it with `PersistMode::SyncAll` when any
  change must be synced (`node/host/src/storage/writer.rs:203-256`). After a failed flush the writer takes no
  more writes, and the node halts until a restart (`storage/mod.rs:13-16`, `writer.rs:261-267`).
- So a reply that a step ran implies its log entry was fsynced, and a step's writes are one batch. VOS patches
  fjall's `lsm-tree` so a flush or compaction no longer makes a write batch visible in part (`Cargo.toml:101-108`,
  the fork's `batch-visible-whole`). This run did not inject a power loss.
