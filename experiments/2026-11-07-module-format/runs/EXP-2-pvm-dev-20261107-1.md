## The design, as it ran

- **The platform** is the suite's process (`binding/src/binding.rs`). It admits releases, keeps each provider's
  history and acceptances, and is the credential proxy, the state store, the egress layer and the cross-module
  router. It writes every lookup event, state read, outbound call record and cross-module call record from what
  crossed a pipe, never from what a guest says. A worker names no provider: the platform knows it by the pipe
  (`DEC-9`).
- **One worker process per provider** (`rutent-pvm-worker`), under `sandbox-exec` with no network, no file writes
  and no fork. It runs the provider's two parts as two PolkaVM instances. `process` is the worker's OS process id;
  `restart` stops that worker alone, starts a new one and loads the running release into it. An upgrade loads into
  the same worker, and a release that doesn't start leaves the running one in place. The worker compiles the
  admitted blob itself, and the platform refuses to run it unless its digests are the admitted ones.
- **The admitting compiler** (`rutent-pvm-admit`) is a fresh process for each admission, under the same
  `sandbox-exec` profile. It parses each part, checks its imports against that part's allow-list and its required
  exports, and compiles it. Before it is called, both digests are compared with the assertion's, so an altered
  part is refused as that part altered before anything is parsed.
- **The sandboxed part's one channel.** Its only host functions are `rt_input`, `rt_outside` (the contract's
  outside request) and `rt_output`. A request is checked as an `OutsideRequest`, which has no field for a
  secret or a destination, and against its transaction and the release's declared operations, before the outside
  part sees it; its response is checked as an `OutsideResponse`. A sandboxed lookup in the suite's spec is sent
  as an outside request naming a secret: it is refused there, never reaches the outside part or the proxy, and is
  recorded as a lookup with no outcome. A sandboxed state read is an outside request the outside part serves, and is
  recorded as the outside part's read.
- **The outside part's host functions** are `rt_request`, `rt_respond`, `rt_secret`, `rt_state`, `rt_egress` and
  `rt_call`, each answered by the platform against the running release's declaration, never a pending one.
  `rt_egress` checks each hop by name and by connected address, ports the reference double's correct path, and
  delivers to the simulated endpoint only what passes.
- **Signatures** are placeholders, as in the suite (`M2`, `M3`): the platform wraps the sandboxed part's result in
  the provider-role envelope with the declared statement key.

## What couldn't run on arm64

- **The compiler backend and the Linux sandbox** (`G-14`). PolkaVM builds both only on `x86_64`. Here every guest
  ran in the interpreter, in the same address space as its provider's worker. The two parts of one provider were
  therefore separated only by the interpreter, not by sandbox worker processes. Other providers were still
  separated by OS processes.
- **Machine code**, so `build.machine_code` holds a digest of the interpreted blob (`B-10`, `G-18`). The
  worker-versus-admission digest comparison ran, but over blobs, which is trivially equal.
- **Compile determinism** (`B-11`, `G-19`). The suite runner's two-compilation check printed "Not run: this
  platform has no PolkaVM compiler". On `x86_64` Linux it compiles each stand-in in two separate admitting-compiler
  processes and compares the machine-code digests. The worker check also compares each load's digests with the
  admitted ones and refuses to run a mismatch.
- **The Linux restrictions**: `unshare` around the admitting compiler, and PolkaVM's sandbox workers with their
  namespaces, `seccomp`, `no_new_privs` and resource limits (`G-16`, `G-20`, `G-21`), and the CPU needs of `G-17`.
  The binding type-checks and passes `clippy -D warnings` for `x86_64-unknown-linux-gnu` with those paths enabled,
  but has never run on it.
- **The scored run.** `run.sh` is written for both platforms. On `x86_64` Linux it also needs `unshare`, which comes
  with util-linux, and unprivileged user namespaces.
