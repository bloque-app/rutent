# EXP-2-pvm-dev-20261107-2: the PolkaVM binding after review, interpreted, on arm64 macOS

The second development run of `T-008-03`'s PolkaVM binding. It reruns
[`EXP-2-pvm-dev-20261107-1`](EXP-2-pvm-dev-20261107-1.md) after the review of that run's commit, `d272c15`, which
found four defects:

- **The `sandbox-exec` profile allowed by default.** It now denies by default, and probes check it.
- **The Linux path was weaker than documented.** It now has mount and PID namespaces, read-only or empty roots,
  resource limits, `no_new_privs`, and a `seccomp` filter for the admitting compiler. The worker compiles only
  inside its isolation. None of this has run yet.
- **Host calls took the guest's word.** Every one is now bound to the outside request in flight, and a hostile test
  checks it.
- **The digest gate ran after start.** It now runs before anything is instantiated.

Every pvm cell now names this run. As before, it ran against the frozen module-interface contract 1.0.0 but off the
scoring platform (item `exp2-run-platform`), so its cells say `pre-freeze`, a scored run on `x86_64-unknown-linux-gnu`
replaces each, and no outcome rests on it.

**Result.** All four categories' reports passed in `rs` and `c`: no finding, nothing uncovered, `missing_languages`
0, 82 of 82 fixtures and controls exercised in each. Three checks also passed:

- every hostile or malformed part was refused at admission;
- the isolation probes refused the user's files, a signal, the network and a write, for both the worker and the
  admitting compiler;
- the operation-binding test refused an outside part that named another operation than the request in flight;
- the kind test refused a cross-module call whose guest named a declared kind for an undeclared forwarded one.

## What changed from `-1`

### 1. The macOS profile denies by default (`isolation::macos_profile`)

Both the worker and the admitting compiler start under:

```text
(version 1)(deny default)
(allow process-exec (literal "<the program>"))
(allow file-read* (literal "<the program>") (literal "/"))
(allow file-read* (subpath "/usr/lib") (subpath "/System/Library") (subpath "/System/Volumes/Preboot/Cryptexes")
                  (subpath "/private/var/db/dyld"))
(allow sysctl-read (sysctl-name "hw.pagesize") (sysctl-name "hw.pagesize_compat"))
(allow signal (target self))
```

It allows no `mach-lookup`, no network, no write, no other `sysctl`, no other process's information, and no `exec`
of anything but the program itself. Two rules go beyond the brief's list (the program, the system and `dyld` read
paths, signals to itself), each because the program can't start without it:

- **Reading the root directory**, which lists its names. Without it the program aborted before `main` (exit 134).
  This was found by adding rules, one at a time, to a profile that failed: reading the program's own directory,
  `/Users`, `/dev`, `/private/etc`, `/private/var`, `/Library`, `/usr`, `/System`, `/opt`, `ioctl`,
  `mach-lookup`, other processes' information and `exec` each left it failing; reading `/` alone let it run.
- **The two page-size `sysctl`s.** Without them `std` couldn't place its main thread's stack guard page ("failed to
  allocate a guard page: Invalid argument") and aborted. `hw.pagesize` and `hw.pagesize_compat` alone let both
  programs start and the whole run pass.

`-2`'s first profile also allowed every `sysctl` read, its own process information, `/dev/urandom`, `/dev/null`
and metadata reads of six directories. All of these were removed together, and the run passed without them.

`tests/isolation.rs` runs five probes inside each program's isolation, and `run.sh` runs it:

| Probe | Worker | Admitting compiler |
|---|---|---|
| Control: the program runs inside its isolation | allowed | allowed |
| Read the binding's own `Cargo.toml`, under the user's home directory | refused | refused |
| Read a file directly in the user's home directory | refused | refused |
| `SIGTERM` to another of the user's processes, which is still running afterwards | refused | refused |
| A TCP connection to a listener on `127.0.0.1` | refused | refused |
| Create a file in the temporary directory, which doesn't exist afterwards | refused | refused |
| Create a file at the root, `/rutent-pvm-probe` | refused | refused |

Two checks by hand show the test can fail. Under `-1`'s profile, `(allow default)(deny network*)(deny file-write*)
(deny process-fork)`, the worker's read of a file in the user's home directory was `allowed`, and so was its
`SIGTERM` to a `sleep` of the user's, which died. Run with no profile, the same two probes were `allowed`.

### 2. The Linux path (`isolation`, `jail`), written but not yet run

- **Both processes** start under `unshare --user --map-root-user --net --ipc --uts --mount --pid --fork --kill-child
  --mount-proc`, as root of a new user namespace with no network. Then, before reading anything, each sets
  `no_new_privs`, makes every mount private and sets no core files.
- **The admitting compiler**, after creating its engine:
  - pivots its root into an empty `tmpfs` and remounts it read-only;
  - sets limits of 64 open files, no new processes and 8 GiB of address space;
  - installs a `seccomp` filter. The filter kills the process for any architecture but `x86_64` or the x32 ABI,
    allows 36 named system calls, and fails every other with `EPERM`.
- **The worker**, before creating its engine:
  - hides `/home`, `/root`, `/tmp`, `/mnt`, `/media`, `/srv` and the user's home directory under empty read-only
    `tmpfs` mounts;
  - makes every mount read-only, `nosuid` and `nodev` (`mount_setattr`, Linux 5.12 or later);
  - sets a limit of 1024 open files.

  It installs no `seccomp` filter of its own. PolkaVM's sandbox clones its own guest workers, each with namespaces,
  `seccomp` and limits (`G-20`), which a filter here would break.
- **Compiling.** The worker compiles every blob after it has confined itself.
- **Verification.** The code type-checks and passes `clippy -D warnings` for `x86_64-unknown-linux-gnu`, but has
  never run. Its first run will be the scored run's `run.sh`, which may need fixes there. On Linux,
  `tests/isolation.rs` runs the five refusals above. Each of these probes tells one mechanism apart:
  - each program reports process id 1: the new PID namespace;
  - the worker reports `NoNewPrivs=1 nofile=1024 core=0` from `/proc/self/status` and `/proc/self/limits`:
    `no_new_privs` and its resource limits;
  - for both programs, a write at `/` is refused: the read-only root;
  - the admitting compiler can't read `/proc/self/status`: its empty root;
  - the admitting compiler can't open a Unix socket, which a new network namespace allows: its `seccomp` filter.

  The rows that depend on these are not run here.

### 3. Every host call is bound to the outside request in flight

- **The worker** forwards each outside request the sandboxed part sends, and each response, to the platform.
- **The platform** checks the request:
  - the contract's `OutsideRequest` shape;
  - the transaction being served;
  - an operation the running declaration declares;
  - that no other request is in flight.

  It then records that request as in flight for the provider whose pipe it came on.
- **The outside part's host calls** (`rt_secret`, `rt_state`, `rt_egress`, `rt_call`) are refused unless a request
  is in flight. They run under its transaction and operation, never the guest's:
  - a secret lookup naming another operation is refused as `undeclared_secret` and recorded under the operation in
    flight;
  - an outbound call naming another operation is recorded under the operation in flight, refused at its first hop as
    `undeclared_operation`, and sends nothing;
  - a cross-module call's kind is the forwarded operation's own (`OperationKind::of`); a kind the guest names that
    differs is refused as `undeclared_kind`.
- **Calls that can't be recorded.** An outbound call to something that isn't `scheme://host:port`, and a
  cross-module call asking something that is no operation kind, are refused and counted in the run's report
  ("host calls refused before a record": 0 in this run).
- **The test.** `an_outside_part_naming_another_operation_than_the_request_in_flight_gets_neither_its_secret_nor_its_destination`
  declares two operations, `op.a` with destination `a`, and `op.b` with destination `b` and secret `b.token`. It
  runs a module whose sandboxed part asks for `op.a` while its outside part looks up `b.token` and calls `b` under
  `op.b`. In both languages:
  - the lookup was recorded under `op.a` and refused as `undeclared_secret`, and the proxy delivered nothing;
  - the call was recorded under `op.a` and refused as `undeclared_operation`, and `b` received nothing.

  The honest control, which asks for `op.b`, resolved the secret and reached `b`. The refused call's record passes
  the contract's `validate_record`.
- **The kind test.** `a_cross_module_call_is_judged_by_the_kind_of_the_operation_forwarded_not_the_kind_the_guest_names`
  has a caller that declares only `deposit` of a running callee, and whose guest names `deposit`. The operation the
  platform would forward is the withdrawal it is serving. In both languages the call was refused as
  `undeclared_kind`, its record names the kind `withdrawal`, and the callee received nothing. The record passes
  `validate_call` and `validate_call_against`. Before this fix the guest's `deposit` was what was checked, so the
  call would have been delivered.
