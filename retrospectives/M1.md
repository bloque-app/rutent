# M1 retrospective

`M1` froze the five contracts, gave each a conformance suite, and ran `EXP-1` (runtime host) and `EXP-2` (module
format). This page says what worked, what didn't, and which lessons should change the method. Facts come from the
commits on `m1`, the feature notes under `features/`, and the experiments' records.

## What worked

- **Contract first, then suites, then candidates.** Both experiments were scored by suites written before either
  candidate existed, so the comparison was fair by construction. Both candidates of each experiment passed the
  suites; the decision then rested on the gap rows, as the method intends.
- **Breakers that only one check flags.** Every suite carries deliberately broken implementations, each caught by
  exactly one check. Reviewers repeatedly used this to show a check could fail, and to find the ones that couldn't.
- **Fresh reviewers on every change.** Almost every round found real defects: fail-open checks, secrets reachable
  through Debug output, a sandbox that allowed by default, a contract flaw letting a statement key mint release keys.
  None of these was found by the author.
- **The scoring platform in CI.** x86_64 Linux runs went through GitHub's runners from `exp2/` branches, so nothing
  was downloaded onto the lead's machine, and every scored number names a run anyone can open.
- **Rulings written down where they apply.** Owner rulings came through the form or were relayed from chat; the
  lead's own rulings sit in each feature's notes, so the external reviewer can see why each line was drawn.

## What didn't

- **The router contract took six review rounds.** Each round's author added checks beyond the findings, and each
  addition gave the next reviewer new ground. It converged only after the lead drew a scope line (structure in
  `T-004-01`, recomputation in `T-004-02`) and gave each review an exit rule.
- **Self-scoring bias in both experiments.** The authors of the purpose-built store and of both bindings scored
  their own columns. Independent audits changed about twenty of the store's cells, most of them missing capabilities
  marked "does not apply", and a dozen of `EXP-2`'s (binding work marked as format passes, passes resting on unrecorded runs).
- **Isolation claims outran the probes.** Three times a sandbox described as deny-by-default wasn't: an
  allow-by-default macOS profile, inherited file descriptors, and process information and sysctl reads left open.
  Each was found only when a reviewer ran a probe.
- **The security review came after the freeze.** `DEC-20`'s separate security review found a high-severity flaw in
  the frozen contracts, so the contracts went to 2.0.0 a day after 1.0.0. Nothing was released, but the order was
  wrong.
- **Shared scoring tables.** Two agents filling different columns of the same rows conflicted on every merge; the
  lead merged cell by cell by script each time.
- **Process slips.** The disk filled and stalled every agent; one agent used `git stash` against the rule; one
  build wrote into a shared global build directory; one push went out with a failing check, because a command chain
  didn't stop on the failure. Each was fixed when found, and the chains now stop on failure.

## Lessons that change the method

These go to the methodology store as proposals (Narthex `REQ-CHN-18`, `XC-4`). None changes rutent's plan.

1. **Security-review the contract paths before a freeze, not after.** A freeze task should depend on a passed
   security review of every `DEC-20` path it freezes.
2. **Audit every experiment's scores independently before its outcome.** An author must not be the last to judge
   its own candidate's cells. The audit applies one standard across columns, and a missing capability is a fail.
3. **Give every review an exit rule and a scope line.** A brief says what the reviewer may raise and when to
   approve, and lists what is deferred, so rounds converge.
4. **A standard isolation probe list.** Any sandbox claim is scored only on probes that try, from inside: a file in
   the user's home, a signal to another process, process and hardware information, TCP and Unix connects, a file
   write, starting a process, and reading an inherited descriptor.
5. **One scoring file per candidate.** Rows are keyed; each candidate's cells live in their own file, and the sheet
   is generated, so parallel runs never edit the same lines.

pieces. Each is recorded here so the owning task inherits it.
