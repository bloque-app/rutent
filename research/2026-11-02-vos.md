## 1. What VOS is at this commit

### Purpose

- VOS core is a Rust runtime for replicated, gas-metered guest programs, run by one operator or by mutually trusting
  operators. `Doc` `docs/design/core-model.md:152`, `:172`
- The stated aims are JAM-compatible agents, independently compiled actors, private state, proofs for chosen methods
  and large tables. `Doc` `docs/design/core-model.md:86-108`
- The README calls it "under construction". `Doc` `README.md:3`

### What runs what

| Layer | What it is | Evidence |
|---|---|---|
| Node | A `vos` process: fjall storage, QUIC peers, one Raft group per replicated agent, a binary API, a machine pool, an optional prover | `Code` `Cargo.toml:3-41`, `node/cli/src/main.rs:166-171`; `Doc` `docs/design/core-model.md:153`, `:978-981` |
| Agent program | A guest PVM program with refine and accumulate entries. It hosts the actors and serves their host calls | `Code` `agent/default/src/`, `agent/wire/src/abi.rs:1-5`; `Doc` `docs/design/core-model.md:198-199`, `:324-326` |
| Actor | A guest program run as an inner machine, reached only through the actor ABI and precompiles | `Code` `agent/wire/src/abi/surface.rs:57-59`, `agent/wire/src/abi.rs:203-313` |
| Workflow | The one kind of guest code that suspends across refines, by memory snapshot | `Code` `agent/wire/src/abi.rs:263-300`, `agent/wire/src/records.rs:218-222`; `Doc` `docs/design/core-model.md:543-554` |
| Gateway | A separate process translating HTTP and SSH onto the node API, holding no authority | `Code` `node/http/src/routes.rs:115-126`; `Doc` `docs/design/node-api.md:510-514` |
| Venue | A trait for anchoring state roots and submitting proofs at a chain. No client reaches a production build | `Code` `node/venue/src/lib.rs:7-16`, `justfile:451-457` |

**A call's path.**

1. A client signs a call. Ingress checks the signature and logs the session key as the caller. `Code` `node/host/src/calls.rs:298-306`
2. The leader batches inputs and refines the batch. The result is what gets proposed. `Code` `node/host/src/leader/execute.rs:109-117`, `:131-153`
3. Followers apply the result and do not re-execute. `Doc` `docs/design/core-model.md:463`, `:981`
4. The reply comes from applied state. `Doc` `docs/design/core-model.md:478-486`

## 3. Each goal against VOS

### PS-10: standalone, reusable components. Does not help; constrains if components are written as actors

- VOS has no notion of these three components. It supplies a runtime in which they could run. `Inference`
- `vos-sdk` is `no_std`, guest-only, and speaks the VOS ABI. `Code` `agent/sdk/src/lib.rs:9`, `:1-4`
- A component whose logic imports SDK types is not reusable outside VOS. Reuse would need its logic kept free of those
  types, behind a thin actor wrapper. `Inference`
- A state machine built on workflows would rely on VOS's snapshot continuation, which is a runtime feature, not a
  library. `Inference`, from `docs/design/core-model.md:561`
- A component linked with AGPL `vos-sdk` carries that licence question wherever it is reused. Whether it binds is a legal
  reading I cannot settle. `Inference`
- The Apache-2.0 PVM crates can be taken separately: the runtime crate `vos-pvm` depends on `vos-pvm-program` and
  `vos-pvm-poseidon2`, not on `vos-wire` or `vos-sdk`. So partial reuse of the VM alone looks possible, and it would bring none of the state, log or
  API. `Code` `pvm/runtime/Cargo.toml:2`, `:22-24`; `Inference`

### PS-12: independent deployment and operation. Helps, with operational constraints

**Helps:**

- A production build carries no chain client, so a node needs no external system. `Code` `node/venue/src/lib.rs:7-8`, `justfile:451-457`
- The node holds its own storage, consensus and API. `Code` `Cargo.toml:3-41`
- The gateway is separate and holds no authority. `Doc` `docs/design/node-api.md:510-514`

**Constrains:**

- The JIT needs Linux on x86_64 with kernel 6.7 or later, or the node falls back to the interpreter, which misses the
  invocation budget (85 µs against 50 µs). `Code` `pvm/runtime/src/backend.rs:103-118`; `Doc` `docs/design/core-model.md:1388`
- The build uses a pinned nightly Rust and, by default, native CPU codegen, documented as non-portable between hosts.
  `Code` `rust-toolchain.toml`, `.cargo/config.toml`
- There is one node key, it is the anchor key, and it has "no rotation". Loss or compromise means replacing the node.
  `Doc` `docs/operations.md:32-34`, `:50-65`
- "A restored backup or a cloned store counts as a compromised node key", and can end a space at its venue for good.
  `Doc` `docs/operations.md:67-72`, `:132-135`
- A store in another layout is refused at open. I found no documented upgrade path for node software at this commit.
  `Doc` `docs/design/core-model.md:928-934`
- Observability is `tracing` logs and the `Stats` and `Status` operator reads. No metrics exporter crate appears in `node`
  or `agent`. `Code` `node/cli/src/main.rs:141-142`, `node/api/src/lib.rs:67-68`

### PS-18: hot-loading providers. Helps, with gaps around the lifecycle

**Helps:**

- An install is an operator request served by a running node. Programs are derived off the runtime thread and a failed
  derivation fails the install, not the node. `Code` `node/host/src/node/admin.rs:241-263`
- It reaches replicas through the agent's log, so replicas switch at one log position. `Code` `agent/wire/src/batch.rs:351-369`; `Inference`
- New invocations take the new program. A live workflow keeps the program it started on, which it pins. `Code`
  `agent/wire/src/records.rs:220-222`, with tests at `node/host/tests/cluster/workflows.rs:174-178`, `:224-228`

**Gaps:**

- An install at an existing instance overwrites the record. Nothing compares the old and new schema or state format.
  `Code` `agent/default/src/refine/admin.rs:55-58`, `:194-219`, `node/host/src/node/admin.rs:338`. State migration is
  open. `Doc` `docs/design/core-model.md:1643`
- There is no uninstall or retire. `Admin` has `Install`, `SetRole` and `ReportEveryWindow`. `Code`
  `agent/wire/src/batch.rs:351-382`. Withdrawing a provider would mean overwriting it with another program or revoking
  roles, and only the second is a native operation. `Inference`
- The previous `Installed` record is not kept, so version history is not in state. `Code` `agent/default/src/refine/admin.rs:55-58`
- Canary, staged rollout and rollback are not provided. Rollback would be a fresh install of the old ELF, subject to the
  same missing state check. `Not in code`; `Inference`

**One agent or many.** This choice shapes how much hot-loading isolates, and PS-18 does not settle it.

- Providers as instances of one agent share a log, a batch and a refine budget, and can call each other synchronously
  and atomically. `Doc` `docs/design/core-model.md:283-287`, `:503-513`
- Providers as separate agents isolate those, but crossing between them is possible only from a workflow, and a handler
  cannot await another agent. `Code` `agent/wire/src/abi.rs:270-277`; `Doc` `docs/design/core-model.md:286-287`

### PS-19: shared and per-transaction state. Helps; caps and identity are VOS's

**Shared state** maps to an instance's Linear state: a struct row, tables and committed maps.

- One instance cannot reach another's rows: the agent keys every row by the calling instance. `Code`
  `agent/default/src/refine/invocation/memory.rs:14-24`, `agent/wire/src/abi.rs:15-21`
- Caps: key 1 KiB, value 64 KiB, 256 KiB of writes per step. `Code` `agent/wire/src/abi/cap.rs:13`, `:17-18`
- I found no total storage quota per instance. `Not in code` (grep for quota in `agent/wire`, `agent/default`, `node/host`)

**Per-transaction state** has two possible mappings. VOS names neither as such. `Inference`

- A workflow's own memory, kept by snapshot. Up to 2.25 MiB held, with 16 MiB writable. `Code` `agent/wire/src/abi/cap.rs:45`, `:78`
- Rows keyed by a transaction id the caller supplies, in shared state. `Inference`

**Consequences of those mappings:**

- A method in PS-19's sense is a handler or a workflow. A handler runs to completion within one refine and keeps nothing
  between calls except rows. `Doc` `docs/design/core-model.md:503-504`
- At most 65,536 unended workflows per agent. `Code` `agent/wire/src/defaults.rs:232`
- An ended workflow's result is kept one hour. `Code` `agent/wire/src/defaults.rs:235`
- An await's deadline defaults to 60 s but can be set up to `u64::MAX` ms, and on the VOS target pages are kept until the
  workflow ends. Long waits look possible on VOS's own limits. `Code` `agent/wire/src/defaults.rs:228`,
  `agent/sdk/src/context.rs:307-313`, `agent/wire/src/abi/cap.rs:228`
- A workflow resumes on another agent's reply, a timer, or a served read. No client input resumes one directly, and
  external signals are an open question. `Code` `agent/wire/src/batch.rs:106-191`, `agent/default/src/refine/inputs.rs:93-96`;
  `Doc` `docs/design/core-model.md:1650`

**"Uniquely identified":**

- VOS has several identifiers: (session, agent, sequence) for calls, a binding digest for credentialed calls, and a
  workflow number the agent assigns and never reuses. `Code` `agent/wire/src/batch.rs:219-226`, `:202-216`, `agent/wire/src/ids.rs:51-54`
- A running handler or workflow is not told any of them. Its context gives agent and instance, caller, time and random.
  `Code` `agent/sdk/src/context.rs:137-199`, `:370`, `agent/wire/src/abi.rs:261`
- So a single transaction identifier would have to be rutent's own, passed in the arguments. `Inference`

**Atomicity.** A step and its synchronous call tree commit or abort together within one agent. Earlier workflow steps
stay committed and multi-step atomicity "uses reservation (saga) patterns". This bears on SPEC's blocked atomicity
invariant and `OQ-9`, without resolving them. `Doc` `docs/design/core-model.md:505-510`, `:549-551`

### PS-20: languages, compile, sign, upload, sandbox. Mixed

**Languages: hinders.**

- The only SDK is Rust, and the only documented guest toolchain is a Rust nightly on a custom RV64EM target with no
  atomics. `Code` `agent/sdk/`, `pvm/guest/README.md:3-6`, `:15-17`
- No non-Rust guest exists in the tree. The `.c` and `.py` files present are tooling. `Code` file search
- The compiler takes an ELF, not Rust, so other languages are not excluded in principle. `Code` `pvm/compiler/src/derive/mod.rs:1-4`, `:225-237`; `Inference`
- Another language would have to supply: an RV64EM target with relocations kept, the host-call instruction sequence,
  the ABI operations, the codec, `_start` routing, and the `.vos_schema`, `.vos_heap` and `VOS_ATTEST` sections.
  `Code` `pvm/guest/README.md:5-6`, `:19-20`, `pvm/compiler/src/derive/mod.rs:14-15`, `:32-36`, `:177-183`, `agent/wire/src/abi.rs:203-313`
- A runtime-heavy language must fit a 512 KiB handler heap and a default gas of 10M, which is about 330 gets or 150 puts,
  at most 100M a handler. `Code` `agent/wire/src/abi.rs:58`, `agent/wire/src/defaults.rs:60-66`. Whether a garbage-collected
  or interpreted language fits is untested here. `Inference`
- Attestable kernels are built by following relocations, and a missed target traps, which makes dynamic dispatch a hazard
  for proved code. `Code` `pvm/compiler/src/derive/mod.rs:20-28`

**Compile: helps.** The derivation from ELF to programs is described as bit-reproducible, and the install records the ELF's
hash and the transpiler's version. `Code` `pvm/compiler/src/derive/mod.rs:65-67`, `agent/wire/src/records.rs:20-24`

**Signed: not in code.** The node checks no publisher signature. `Not in code`

- The one signature on an install is the operator's envelope, which says who may install, not who wrote the module.
  `Code` `node/host/src/api/operator.rs:217-258`
- Operator keys are "all trusted alike". `Doc` `docs/design/node-api.md:293-294`

**Upload: operator only.**

- The API's only route for code is the operator's `Install`, up to 64 MiB. `Code` `node/api/src/lib.rs:54-74`, `agent/wire/src/abi/cap.rs:11`
- There is no publisher role, registry or catalogue operation. `Not in code`

**Sandbox: helps, within a boundary I could not assess.**

- Enforced limits: PVM memory isolation, gas per step, mediated host calls, a per-kind table of allowed operations
  enforced at run time, per-step caps on writes and messages, and a machine reset between uses. `Code`
  `agent/wire/src/abi.rs:27-32`, `agent/wire/src/abi/cap.rs:217-233`; `Doc` `docs/design/core-model.md:175-176`, `:340-341`, `:377-386`
- A trap, gas exhaustion or cap failure fails the step, not the node. `Code` `agent/wire/src/abi/codes.rs:68-74`; `Doc` `docs/design/core-model.md:506-508`
- Outbound I/O: none. The actor surface is the `0x500..0x5ff` ABI and precompiles, and none of its operations touches a
  network. Unknown ids answer `WHAT`. `Code` `agent/wire/src/abi/surface.rs:57-59`, `agent/wire/src/abi.rs:27-30`, `:203-313`.
  `Cargo.lock` holds no reqwest, hyper, ureq, isahc or curl. `Code`. The extension host that might provide this is open.
  `Doc` `docs/design/core-model.md:1672-1680`
- So a provider module cannot reach its provider from inside the sandbox at this commit. The I/O would sit in a process
  outside it, pushing results in as signed calls. `Inference`
- Inbound webhooks cannot reach a module as such: gateway routes take the node API's encoded, signed bodies. `Code`
  `node/http/src/routes.rs:115-118`; `Inference`
- Secrets: "a space's operators see everything in it", state is not encrypted, and encrypted private agents are a
  non-goal. Bytecode is visible to the space. `Doc` `docs/design/identity-and-authority.md:56`, `docs/design/core-model.md:117`,
  `:319`. No encryption code in the node or agent paths searched. `Code` grep
- A second layer: no seccomp or landlock appears in `pvm` or `node`. `Not in code`. PVM execution is part of the node process,
  whose key sits in its store and whose `operator.key` sits in its data directory by default. `Doc`
  `docs/design/core-model.md:153`, `docs/operations.md:15-16`, `:32-33`. So an escape would reach those. `Inference`
- The JIT is about 8,900 lines of native code generation over untrusted input, and is the default backend. `Code`
  `pvm/runtime/src/recompiler/`; `Doc` `docs/design/core-model.md:405-407`
- The documented external audit's scope is the proof stack and `derive`. It does not name the runtime as a sandbox. `Doc`
  `pvm/proof/SECURITY.md:469-490`

### PS-21: provable and auditable, who, what, when, outcome. Partly helps; several gaps

**Helps:**

- Client calls and operator commands are signed, and operator write commands carry a recorded nonce. `Code`
  `node/host/src/calls.rs:298-306`, `node/host/src/api/operator.rs:217-289`
- A work result records per step: input reference, outcome, instances run, writes, messages and gas. `Code` `agent/wire/src/result.rs:18-25`, `:243-262`
- Committed maps give Merkle roots and proofs. `Doc` `docs/design/core-model.md:753-755`
- Window roots can be anchored and methods proved, with a masked proof. `Doc` `docs/design/core-model.md:805-815`, `:1194-1200`

**Gaps against "who did what, when, and the outcome":**

| Gap | Evidence | Tag |
|---|---|---|

## 4. What adopting VOS would mean for the requirements

Stated as consequences. `SPEC.md` states what, never how (`PS-62`), so VOS's terms belong in `suggestions/` and any of the
following would reach the spec only in mechanism-free words. "This commit" means the pinned one. Each item could change.

Everything in this section is `Inference` from the tagged facts in sections 1 to 3.

### Requirements it would add

1. **`REQ-MDL-*`, an I/O boundary.** The spec would need to say where a provider's outbound and inbound I/O lives, and what
   of a provider sits outside the sandbox, since the sandbox has no network. `PS-20`'s safety restrictions would then cover
   only part of each provider. The outside part would need its own signing, upload and audit rules, or a statement that
   they do not apply.
2. **`REQ-MDL-*`, secrets.** The spec would need to say where a provider's credentials live, since module state is readable
   by operators and unencrypted.
3. **`REQ-MDL-*`, state compatibility on upgrade.** Upgrades overwrite without checking state format, so the spec would need
   to place that check somewhere.
4. **`REQ-MDL-*`, withdrawal.** Removing a provider is not a platform operation, so the spec would need to define what
   withdrawing means.
5. **`REQ-AUD-*`, an audit store apart from the log.** A complete trail would need retention independent of log compaction,
   holding inputs, signer identity and evidence the log does not hold.
6. **`REQ-AUD-*`, operator actions.** Which operator key installed a module or granted a role would have to be captured by a
   layer that does not exist at this commit.
7. **`REQ-STM-*`, `REQ-MDL-*`, a transaction identity.** The platform's identifiers are not exposed to guests, so rutent's own
   would have to be defined and passed in.
8. **`REQ-OPS-*`, placement.** The one-agent-or-many choice would need a stated isolation requirement behind it.
9. **`OBL-*`, operator obligations.** No node restored from backup, node keys never rotated but replaced, firewalling of
   `api_listen`, a Linux kernel floor for the JIT. `docs/operations.md:14`, `:32-34`, `:67-72`
10. **`ASM-*`, new assumptions.** All nodes of a deployment trust each other, local disk is trusted, and operators can read
    everything. `docs/design/core-model.md:172-174`
11. **`REQ-MOD-*`, a licence constraint.** The AGPL host, and an SDK under the same licence, would need stating against how
    modules are licensed and how `PS-10`'s components are reused.

### Requirements it would tighten

1. **`REQ-MDL-*`, resource limits.** Handler heap 512 KiB, default gas 10M and at most 100M, value 64 KiB, key 1 KiB, request
   and reply 64 KiB, 256 KiB of writes and 16 messages a step, program up to 64 MiB. `PS-20`'s "safety restrictions" would have
   these as their floor unless changed in VOS's consensus constants.
2. **`REQ-ORD-*`, order lifetime.** At most 65,536 unended workflows per agent, and results kept an hour after ending, if orders
   are mapped to workflows.
3. **`REQ-ORD-*`, atomicity.** Atomic only within an agent's step, with sagas beyond. Under a one-agent placement, more would be
   atomic but less isolated.
4. **`REQ-CAT-*`, catalogue roles.** Only operators install, so a third party publishing a module needs a path through an
   operator.
5. **`REQ-AUZ-*`, authorisation.** A single role byte per principal would be the base unless a policy layer sits above it.
6. **`NFR-*`, latency and throughput.** Bounds could not yet cite evidence beyond one host.

### Goals that could not be satisfied at this commit without work not in the tree

| Goal | What is missing | Could be added by |
|---|---|---|
| A module reaching its provider from inside the sandbox (`PS-20`, with `PS-15` to `PS-17`) | Any outbound channel | Extension host, open upstream, or rutent's own |
| A platform-verified publisher signature on a module (`PS-20`) | The check itself | A layer before `Install`, or upstream's return of package signing |
| Authoring modules in several languages with support (`PS-20`) | Every SDK but Rust's | Per-language ABI and section tooling, then gas and heap fit |
| Proof of who changed a provider, surviving compaction (`PS-21`) | Operator identity and durable history | A layer outside the log, or a change to the input record |
| Provability to a party who does not trust the operator (`PS-21`) | Evidence retention, a venue client in production builds, the external audit | Upstream's roadmap or rutent's own, with the trust model unchanged for anything not proved |
| Mutually distrusting parties in one deployment (`PS-23`) | Byzantine tolerance, a stated non-goal | Separate spaces and a cross-space protocol, which is a draft |

### What it would leave untouched

The three provider categories and their semantics (`PS-14` to `PS-17`), quoting and routes, conservation of value, what
"route" means, custody, and external authentication beyond client keys. VOS has no opinion on any of them. `Inference`

### Threat areas in `SPEC.md` section 8, as VOS would change them

| Area | Change |
|---|---|
| Module supply chain | No publisher check at the platform, so the threat stays open until something else provides one |
| Sandbox escape and resource abuse | A defined boundary with gas and caps, but a JIT in the node's process, no second layer, and no named audit of it. No per-instance storage quota |
| Isolation of shared and per-transaction state | Enforced row keying by instance, machine reset covered by a differential proptest |
| Quote and route manipulation | Not touched |
| Repudiation and audit tampering | Operators can log any origin. This area would need mitigation outside VOS or an accepted-risk item |
| Authorisation bypass at the external boundary | The gateway holds no authority, which removes a class of bypass. The node checks each signature |
| Denial of service | Limits per address at the gateway, admission control and a verification budget at the node |

## 5. Risks

**Maturity.**

- The branch's own 1,120 commits are dated over 25 days, on top of reused PVM and prover code, and the README calls it under
  construction. `Code` git history; `Doc` `README.md:3`, `docs/design/core-model.md:1597-1605`
- Formats still move: every segment-format bump changes every program id and is "a governance event", and a new store layout
  is refused at open rather than migrated. `Doc` `pvm/proof/SECURITY.md:173`, `docs/design/core-model.md:928-934`
- `master` and `vos-core` differ enough that docs and third-party knowledge of VOS may describe the other one. `Code`
- The most-cited numbers miss their targets or come from one machine. `Doc` `docs/design/core-model.md:1403-1405`

**One organisation, largely one person.**

- One author wrote nearly all commits, and no releases exist to pin to. `Code` git history
- The build depends on forks under a personal account: `olanod/stwo` for the prover, `olanod/lsm-tree` under the storage engine.
  `Code` `Cargo.toml:108`, `:258-259`
- `cipher-clerk` and the optional `s4` are git dependencies on Codeberg's `Virto`. `Code` `Cargo.toml:241`, `node/gateway/Cargo.toml:35`
- A live chain venue depends on a pallet another team would implement. `Doc` `docs/design/spaces-pallet.md:1-14`
- AGPL with no linking exception narrows who can reuse a fork or module without a further grant. Whether that matters depends on
  questions below. `Inference`

**Security properties claimed but not demonstrated here.**

- **Sandbox strength.** Claimed by design. I found no fuzz target for the JIT or for containment, no second layer and no named audit.
  The conformance vectors test semantics, not containment. `Code`; `Inference`
- **Zero knowledge and soundness of proofs.** Marked met in the docs, while the external audit "before value" is outstanding,
  parts of the AIR are "not yet under a forgery gate", and the bit counts are unreviewed. `Doc` `docs/design/core-model.md:1209-1228`, `pvm/proof/SECURITY.md:39`, `:72-76`
- **The fork's open divergences** are documented as items the wraps' counts rest on. `Doc` `pvm/proof/SECURITY.md:265-275`
- **Vendor-signed packages.** Claimed in the model, absent in code. `Not in code`
- **Machine reset non-leakage.** The docs say a differential test gates it, and proptests compare released and kept machines with
  fresh ones. I did not run them, and they test equivalence under their generated sequences, not an attacker. `Doc`
  `docs/design/core-model.md:387-388`; `Code` `pvm/runtime/src/pool/tests.rs:863`, `:904`
- **Cipher-clerk.** A design review in the repository records a critical gap in its currency check. The node depends on it at
  v0.3.0, and I could not determine whether that tag has the fix. `Doc` `docs/design/identity-and-authority.md:1027-1029`; `Code` `Cargo.toml:241`

**Coupling.** VOS's consensus constants, ABI and formats would become rutent's compatibility surface, and a change upstream
would be a change to rutent's modules. `Inference`

## 6. Questions only the owner can answer

Each is plain. None is added to the form.

1. Which VOS do you mean: `vos-core` at this commit, `master`, or where `vos-core` is heading? The answer changes most of section 3.
2. What did you want VOS for: the module sandbox alone, the whole runtime including replicated state, or the proofs?
3. Would partial use count, such as the Apache-2.0 PVM crates alone?
4. Must a provider's network I/O run inside the sandbox, or may a provider be split into a sandboxed part and an outside part?
5. Do you have any knowledge of upstream's plans for the extension host, package signing and dates, beyond this repository, that
   may be relied on? If so, may the spec cite it?
6. Is there a working relationship with the VOS owner that would allow requirements to be fed upstream, or must rutent treat VOS
   as it is?
7. Who must be able to verify the audit trail: the operator only, a regulator trusting the operator's records, or a party who does
   not trust the operator?
8. Must third parties write provider modules, or is that for now only the operator's own team? This decides how much the absent
   publisher role matters.
9. May third-party modules be AGPL-bound, and is rutent itself able to accept AGPL dependencies, given the Bloque Open Source family's
   licence choices?
10. May operators read provider credentials and module state? If not, what holds them?
11. May rutent depend on an external chain for provability, given `PS-12`'s decoupling goal?
12. Which languages does "a wide range" have to mean on day one?
13. Would an external security audit of the sandbox be a condition of any adoption, and who would pay for it?
